# M3 — Galaxy Z Fold6 학습 실측

기기: SM-F956N (Snapdragon 8 Gen 3, Adreno 750), Android 16.

## 학습이 동작하기까지 (v0.3.0 → v0.3.5)

| 버전 | 증상 | 원인 / 조치 |
|---|---|---|
| v0.3.0 | 학습 시작 시 `vkCreateComputePipelines: VK_ERROR_UNKNOWN` | 역전파 셰이더의 specialization constant 크기 배열 의심 → 고정 크기로 |
| v0.3.1~0.3.3 | 학습은 돌지만 어떤 설정이든 흐리고 미리보기가 안 바뀜 | 자가 검사: 순전파는 CPU와 일치, **그래디언트 전부 0** (장면 맞추기 24.9 → 24.9 dB) |
| v0.3.4 | 그대로 | 단계별 검사: 순전파 기록·갱신 단계 정상, **shared 역전파 출력만 0** (36쌍 중 1쌍). 공유 메모리 atomic은 정상 |
| v0.3.5 | **해결** | 순전파와 같은 구조의 serial 역전파(단일 반복문, 가우시안 하나씩) → 그래디언트 일치, 장면 맞추기 24.9 → 36.5 dB. 학습 전 폰 GPU에서 변형별로 검증해 맞는 것만 사용 |

- 원인이 된 구조: barrier가 **중첩 반복문** 안에 있고 반복 횟수를 공유 메모리에서 읽는 셰이더. Adreno 드라이버에서 결과가 0 (컴파일 오류 없음).
- subgroup 산술: 기능 하나씩(basic / elect / id / float add / ballot)은 컴파일되지만 조합한 셰이더(probe, 학습 역전파)는 `VK_ERROR_UNKNOWN`. 원인 조합 미확인.

## 첫 실제 학습 (v0.3.5)

lizard (점 구름 3만 개 — 배경이 거의 없는 예전 zip), 빠름: 360×640, 2000회, 배경 제거 없음.

| 항목 | 값 |
|---|---|
| 준비 | 불러오기 1.5 s · 초기화 0.2 s · GPU 준비 0.5 s · 역전파 검증 0.9 s |
| 학습 시간 | 100.7 s (2000회) |
| ms/회 (500회 단위) | 28 → 39 → 61 → 73 (가우시안 3만 → 6.5만) |
| GPU ms/회 (2000회 근처) | 투영 0.3 · 정렬 2.1 · 렌더 4.4 · **역전파 30.4** · 최적화 6.4 (합 43.6) |
| 가우시안 | 30,000 → 65,141 (densify +35,142 / −1) |
| 검증 PSNR | **21.93 dB** (23장) |
| 학습 뷰 PSNR 추이 | 12.4 → 13.6 → 13.2 → 15.5 → 18.8 → 20.3 → 21.1 → 21.1 → 21.6 → 22.4 |
| 발열 | LIGHT, 배터리 36.1°C 유지 |

관찰:
- 역전파가 GPU 시간의 70%. serial은 가우시안마다 barrier 2번 → subgroup 경로를 살리는 것이 가장 큰 속도 개선 후보.
- 벽시계 76.5 ms/회 vs GPU 합 43.6 ms → 단계마다 제출·대기 2번, 결과 읽기 등으로 약 30 ms가 GPU 밖에서 쓰임 → 단계 합치기·간접 dispatch로 줄일 수 있음 (M5).
- 처음 600회는 PSNR이 거의 그대로(SH 0차, densify 시작 전) → 학습률·스케줄 조정 여지 (M4).

## 인물 데이터셋 (v0.3.5)

body (전신 캐릭터, 마스크·깊이 있음), 빠름: 360×640, 2000회, **배경 제거 켬**.

| 항목 | 값 |

| 학습 시간 | 104.9 s (2000회) |

| 가우시안 | 41,465 → 35,662 (densify +1,576 / 제거 −7,379) |
| 검증 PSNR | **40.10 dB** (23장, 배경 포함 — 배경은 맞추기 쉬워 인물만 잰 값보다 높게 나옴) |
| 학습 뷰 PSNR 추이 | 24.2 → 33.0 → 35.7 → 38.1 → 38.9 → 39.1 → 40.2 → 41.2 → 40.8 → 42.1 |
| 발열 | LIGHT, 배터리 36.6 → 38.3°C |

관찰:
- 인물 + 마스크 학습은 처음 200회부터 빠르게 수렴 (깊이 초기화가 좋음).
- 역전파가 lizard보다 쌍은 적은데(13.7만 vs 30만) 더 느림(47.8 vs 30.4 ms). serial 방식은 타일마다 그 타일의 가우시안 수만큼 순서대로 돌기 때문에, 인물처럼 가우시안이 몇몇 타일에 몰리면 긴 타일 몇 개가 전체 시간을 정함. 게다가 v0.3.5의 serial은 픽셀이 이미 불투명해진 뒤의(뒤쪽) 가우시안까지 다 돈다 → 타일별 "마지막 기여" 지점에서 멈추게 하면(공유 메모리 트리 최댓값은 폰에서 정상 확인) 바로 줄어들 것.
- 가우시안 수가 줄어드는데 ms/회가 늘어남: 학습이 진행되며 가우시안이 커지고 겹쳐서 타일당 쌍이 늘고, SH 차수가 0 → 3으로 올라감.

## 촬영 형식 시뮬레이션 (PC lavapipe, v0.5.0 이후, 카메라 없이)

`tools/datasets/simulate_capture.py`로 body 데이터셋을 앱 촬영 결과와 같은 형식으로 바꿔 학습(짧은 변 360 → 640×360, 600회, bucket, λ 0.2 → 1.0). 센서 방향(가로) JPEG, ARCore 관례 포즈, 160×90 깊이(30% 프레임은 없음), 절반 해상도 마스크. 기준: 원래 세로 데이터셋 360×640 600회 = 검증 37.18 dB · SSIM 0.9872 · 머리 31.09 dB.

머리 추정 원을 가로 이미지에 투영해 보니 4개 시점 모두 머리에 정확히 맞음 → 이미지 회전·내부 파라미터·포즈·깊이 역투영이 서로 맞음.

| 조건 | 검증 PSNR | SSIM | 머리 PSNR |
|---|---|---|---|
| **촬영 형식, 오차 없음** | **37.04** | **0.9866** | **30.94** |
| 포즈 오차: 느린 드리프트만 (평균 0.6 cm·0.19°, 최대 1.2 cm) | 31.75 | 0.9691 | 25.07 |
| 포즈 오차: 프레임마다 흔들림만 (평균 0.5 cm·0.16°) | 31.68 | 0.9688 | 25.07 |
| 포즈 오차: 둘 다 (평균 0.8 cm·0.24°) | 29.58 | 0.9586 | 23.26 |
| 포즈 오차: 둘 다 ×3 (최대 3 cm·1°) | 23.83 | 0.9159 | 19.93 |
| 마스크 경계 흐림 (6 px 블러) | 34.95 | 0.9742 | 26.16 |
| 마스크 깎임 (4.5 px 침식) | 35.29 | 0.9859 | 27.53 |
| 깊이 없음 (랜덤 초기화) | 33.61 | 0.9218 | (무효) |

- 촬영 형식 자체는 손실 거의 없음(−0.14 dB: JPEG, 절반 해상도 마스크, 깊이 30% 빠짐).
- **포즈 정확도가 가장 큰 위험**: 평균 0.5 cm·0.2° 오차만으로 −5.4 dB, 1 cm 수준이면 −7.5 dB. 2.2 m 거리, 학습 해상도에서 약 2~3 px 어긋남 → 흐림·이중상. 원래 해상도에서는 픽셀로 더 커짐. ARCore 실제 오차는 한 바퀴에 cm 단위일 수 있음 → **학습 중 카메라 포즈 보정**이 필요.
- 마스크 품질: 경계가 흐리거나 깎이면 −1.8~2.1 dB, 머리(머리카락) −3.5~4.8 dB.
- 깊이가 없으면 랜덤 초기화로 600회에서 −3.4 dB.
- 이 결과의 머리 PSNR 버그(랜덤 초기화일 때 머리 추정이 빈 공간에 잡힘)는 고쳤음.

## 녹화하면서 처리 (v0.6.0, PC lavapipe, 카메라 없이)

`gs_live_replay`로 가상 촬영(위의 촬영 형식 clean)을 앱과 같은 경로로 다시 흘림: 프레임마다 RGB → YUV 4:2:0(카메라처럼) → `submit` → `prepare`(변환) → 마스크를 세운 방향 0..1로(ML Kit 출력 대신) → `add_mask`(대상 고르기 + 깊이 판별) → 메모리 데이터셋 + 백그라운드 파일 쓰기. 학습은 360 → 640×360, 600회, λ 0.2 → 1.0.

| 항목 | 결과 |
|---|---|
| 학습 화질 (메모리/파일 같은 내용) | 검증 36.94 dB · SSIM 0.9860 · 머리 30.83 dB (기존 파일 경로 37.04 dB, 차이는 JPEG를 한 번 더 거친 것) |
| 메모리 데이터셋 = 파일에서 다시 읽은 것 | 테스트로 확인: 포즈·마스크·깊이 같음, 이미지는 JPEG 차이만 |
| 마지막 마스크 → 학습 데이터 준비 | 0.1 ms 이하 |
| 파일 쓰기 | 장당 약 22 ms(백그라운드), 촬영 끝 → 저장 끝 약 20 ms |
| 키프레임 한 장 (PC Xeon 2.1 GHz, 1920×1080 입력) | 변환 약 32 ms(1280×720 저장용 + 960×540 학습용), 대상 고르기 4~8 ms, 선명도 0.3 ms |
| 가상 한 바퀴(반지름 1.2 m, 40 s) | 키프레임 121장 |

**대상 고르기** (다른 사람을 마스크에 가상으로 추가: 대상 마스크를 60% 크기로 화면 옆에, 깊이 3.5 m)

| | 다른 사람이 남은 비율 |
|---|---|
| 고르기 없음 (v0.5.0) | 100% |
| 영역만 (몸 중심선에 닿는 영역) | 떨어져 있으면 0%, 화면에서 붙어 보이면 그대로 |
| + 깊이 판별 (3×3 모두 멀어야) | 깊이 있는 프레임 23.7% (윤곽선이 남음) |
| **+ 깊이 판별 (가까운 샘플이 2칸 안에 없으면)** | **깊이 있는 프레임 4.6%**, 깊이 없는 프레임 50.8%, 전체 17.3% |

- clean(다른 사람 없음)에서는 깊이 판별이 한 프레임도 자르지 않음 → 대상의 경계(깊이가 배경으로 번지는 곳)는 보호됨.
- 깨끗한 정답으로 다시 평가: clean 36.94 dB, 다른 사람 추가 37.12 dB, 머리 둘 다 30.83 dB. 다만 가상으로 붙인 사람은 3D로 일관되지 않아(프레임마다 화면 옆에 붙임) 학습이 평균내 버림 — 실제로 서 있는 사람은 3D로 맞아 떠다니는 가우시안이 되므로 지우는 것이 중요.
- 한계: 화면에서 붙어 보이고 깊이도 없는 프레임(ARCore가 아직 깊이를 못 만든 처음 몇 초)에서는 절반이 남음.
