# M3 — Galaxy Z Fold6 학습 실측

기기: SM-F956N (Snapdragon 8 Gen 3, Adreno 750), Android 16.

## 학습이 동작하기까지 (v0.3.0 → v0.3.5)

| 버전 | 증상 | 원인 / 조치 |
|---|---|---|
| v0.3.0 | 학습 시작 시 `vkCreateComputePipelines: VK_ERROR_UNKNOWN` | 역전파 셰이더의 specialization constant 크기 배열 의심 → 고정 크기로 |
| v0.3.1~0.3.3 | 학습은 돌지만 어떤 설정이든 흐리고 미리보기가 안 바뀜 | 자가 검사: 순전파는 CPU와 일치, **그래디언트 전부 0** (장면 맞추기 24.9 → 24.9 dB) |
| v0.3.4 | 그대로 | 단계별 검사: 순전파 기록·갱신 단계 정상, **shared 역전파 출력만 0** (36쌍 중 1쌍). 공유 메모리 atomic은 정상 |
| v0.3.5 | **해결** | 순전파와 같은 구조의 serial 역전파(단일 반복문, 가우시안 하나씩) → 그래디언트 일치, 장면 맞추기 24.9 → 36.5 dB. 학습 전 폰 GPU에서 변형별로 검증해 맞는 것만 사용 |

- 원인이 된 구조: barrier가 **중첩 반복문** 안에 있고 반복 횟수를 공유 메모리에서 읽는 셰이더. Adreno 드라이버에서 결과가 0 (컴파일 오류 없음).
- subgroup 산술: 기능 하나씩(basic / elect / id / float add / ballot)은 컴파일되지만 조합한 셰이더(probe, 학습 역전파)는 `VK_ERROR_UNKNOWN`. 원인 조합 미확인.

## 첫 실제 학습 (v0.3.5)

lizard (점 구름 3만 개 — 배경이 거의 없는 예전 zip), 빠름: 360×640, 2000회, 배경 제거 없음.

| 항목 | 값 |
|---|---|
| 준비 | 불러오기 1.5 s · 초기화 0.2 s · GPU 준비 0.5 s · 역전파 검증 0.9 s |
| 학습 시간 | 100.7 s (2000회) |
| ms/회 (500회 단위) | 28 → 39 → 61 → 73 (가우시안 3만 → 6.5만) |
| GPU ms/회 (2000회 근처) | 투영 0.3 · 정렬 2.1 · 렌더 4.4 · **역전파 30.4** · 최적화 6.4 (합 43.6) |
| 가우시안 | 30,000 → 65,141 (densify +35,142 / −1) |
| 검증 PSNR | **21.93 dB** (23장) |
| 학습 뷰 PSNR 추이 | 12.4 → 13.6 → 13.2 → 15.5 → 18.8 → 20.3 → 21.1 → 21.1 → 21.6 → 22.4 |
| 발열 | LIGHT, 배터리 36.1°C 유지 |

관찰:
- 역전파가 GPU 시간의 70%. serial은 가우시안마다 barrier 2번 → subgroup 경로를 살리는 것이 가장 큰 속도 개선 후보.
- 벽시계 76.5 ms/회 vs GPU 합 43.6 ms → 단계마다 제출·대기 2번, 결과 읽기 등으로 약 30 ms가 GPU 밖에서 쓰임 → 단계 합치기·간접 dispatch로 줄일 수 있음 (M5).
- 처음 600회는 PSNR이 거의 그대로(SH 0차, densify 시작 전) → 학습률·스케줄 조정 여지 (M4).

## 인물 데이터셋 (v0.3.5)

body (전신 캐릭터, 마스크·깊이 있음), 빠름: 360×640, 2000회, **배경 제거 켬**.

| 항목 | 값 |

| 학습 시간 | 104.9 s (2000회) |

| 가우시안 | 41,465 → 35,662 (densify +1,576 / 제거 −7,379) |
| 검증 PSNR | **40.10 dB** (23장, 배경 포함 — 배경은 맞추기 쉬워 인물만 잰 값보다 높게 나옴) |
| 학습 뷰 PSNR 추이 | 24.2 → 33.0 → 35.7 → 38.1 → 38.9 → 39.1 → 40.2 → 41.2 → 40.8 → 42.1 |
| 발열 | LIGHT, 배터리 36.6 → 38.3°C |

관찰:
- 인물 + 마스크 학습은 처음 200회부터 빠르게 수렴 (깊이 초기화가 좋음).
- 역전파가 lizard보다 쌍은 적은데(13.7만 vs 30만) 더 느림(47.8 vs 30.4 ms). serial 방식은 타일마다 그 타일의 가우시안 수만큼 순서대로 돌기 때문에, 인물처럼 가우시안이 몇몇 타일에 몰리면 긴 타일 몇 개가 전체 시간을 정함. 게다가 v0.3.5의 serial은 픽셀이 이미 불투명해진 뒤의(뒤쪽) 가우시안까지 다 돈다 → 타일별 "마지막 기여" 지점에서 멈추게 하면(공유 메모리 트리 최댓값은 폰에서 정상 확인) 바로 줄어들 것.
- 가우시안 수가 줄어드는데 ms/회가 늘어남: 학습이 진행되며 가우시안이 커지고 겹쳐서 타일당 쌍이 늘고, SH 차수가 0 → 3으로 올라감.

## 속도 수정 (v0.7.0, PC)

- **bucket 복귀**: 재선택(500회마다) 때 bucket 상태가 안 맞으면 쌍 버퍼를 지난 구간의 최대 쌍 수에 맞게 줄임. 테스트: 처음 버퍼를 일부러 크게 잡으면 수정 전에는 bucket이 측정되지 않음(실패), 수정 후 측정됨.

- **초기 가우시안 수** (가까이서 찍은 가상 촬영: body를 반지름 1.2 m로, 360 → 640×360, 600회):

|---|---|---|---|---|

| 6만 | 34.42 dB | 29.13 dB | 1.20 s | 23.5만 |

## 학습 중 카메라 포즈 보정 (v0.7.0, PC lavapipe)

사진마다 카메라 축 기준의 작은 회전·이동 보정값을 두고, 그 사진으로 학습할 때마다 같은 역전파에서 나온 그래디언트로 Adam 한 걸음(이동 1e-3 × 범위, 회전 1e-3 rad). 그래디언트는 train_step에서 가우시안마다 (카메라 좌표 위치를 통한 몫 + 투영 공분산의 W를 통한 몫)을 workgroup별로 합하고 CPU에서 더함. 검증 사진은 평가 전에 카메라만 20걸음 맞춤(좋아지면 걸음 1.5배, 나빠지면 최선 위치로 돌아가 절반 — 주어진 포즈보다 나빠지지 않음).

- 정확성: 카메라를 움직이는 것 = 모든 가우시안을 반대로 움직이는 것이므로, 합한 포즈 그래디언트가 가우시안별 그래디언트(CPU 기준과 일치 확인된 것)로 계산한 값과 6축 모두 4자리 일치.
- 복원: 정확히 렌더한 장면에서 카메라 하나를 9.9 cm·1.45° 옮기고 가우시안을 고정한 채 보정 → 0.0 cm·0.04°.

가상 촬영(body, 60장 중 검증 8, 480×270, 1500회), 검증 PSNR (검증 사진 위치 맞춤 후):

| 포즈 오차 | 보정 없음 (주어진 포즈 / 맞춤 후) | **보정** | 재투영 오차 (학습 사진, 360p) |
|---|---|---|---|
| 없음 (정확) | 41.29 / 41.35 dB | 40.63 dB | — |
| 평균 0.8 cm·0.25° | 30.60 / 35.01 dB | **39.68 dB** | 1.89 → **0.21 px** |
| 평균 2.4 cm·0.8° (최대 3 cm·1°) | 24.01 / 28.59 dB | **35.08 dB** | 6.14 → **0.62 px** |

- 포즈가 틀린 경우 +4.7~6.5 dB(맞춤끼리 비교), 주어진 포즈 기준으로는 +9~11 dB. 그림: 3 cm에서 흐려진 얼굴·팔이 보정 후 선명해짐.
- 정확한 포즈에서는 보정이 0.6 dB 손해(보정값이 평균 0.3 cm 흔들림). 학습률을 0.1배로 줄여 가도 같음(40.74 dB). → 직접 찍은 스캔(ARCore)에서만 기본으로 켬.
- 검증 맞춤을 처음에 Adam(3배, 10걸음)으로 했더니 정확한 포즈를 오히려 망침(38.15 → 32.24 dB) → 위의 걸음 조절 방식으로 바꿈. 걸음 수: 12회 33.6, 16회 34.3, **20회 35.1 dB**(3 cm).
- 위치 오차(cm)만 보면 잘 안 줄어 보이는데(2.35 → 1.96 cm), 작은 대상에서는 작은 회전과 옆 이동이 거의 같은 화면 이동이라 구분이 안 되기 때문. 화질에 중요한 재투영 오차는 10배 줄어듦.

## 움직임 보정 (v0.8.0, PC lavapipe)

사람은 한 바퀴 도는 동안 가만히 있지 못함 → 사진마다 고개·팔 위치가 달라 겹치고 흐려짐. SC-GS 방식으로 보정: 초기 가우시안을 k-means한 **제어점 64개**, 사진마다 제어점별 작은 회전·이동, 가우시안은 가까운 제어점 4개를 거리 가중(exp(−d²/2r²), r = 가까운 제어점 3개까지 평균 거리)으로 섞어 따라감(위치는 Σw(R p + b), 방향은 exp(Σw·회전)). 움직임은 포즈 보정처럼 같은 역전파에서: train_step_motion이 workgroup마다 제어점별로 합하고(스레드 하나가 제어점 하나, float atomic 없음) train_motion_sum이 더한 뒤 CPU에서 Adam(이동·회전 벡터마다 2차 모멘트 하나 → 방향 유지). 규제: 크기(decay), 이웃 6개와 단단하게(ARAP), 앞뒤 학습 사진과 비슷하게, **제어점별 평균 움직임 0**(모델이 평균 자세가 되게). 처음 갱신 때 앞뒤 사진의 움직임에서 시작. 300회(×반복/3000)부터. 결과·뷰어·.ply는 움직임을 뺀 평균 자세.

- 정확성: 움직임이 0일 때 제어점 그래디언트 = 가우시안별 그래디언트(CPU 기준과 맞는 것)를 가중합한 값, 최대 오차 5.6e-10 (최대값 3.7e-3).
- 복원: 제어점 하나를 9 cm·11° 움직여 렌더한 사진에 맞추면(가우시안 고정) 화면 위 어긋남 0.64 → 0.12 px.

가상 촬영: body가 고개(끄덕 ±4°, 돌림 ±8°, 기울임 ±3°)·팔(±4~5°)·상체(±1.5~3°)를 사인파 두 개씩 섞어 천천히 움직임(정지 자세 기준 평균 0; 제어점 위치에서 평균 1.1 cm, 최대 6.8 cm 이동). 90장(검증 12), 270×480, 1500회. **같은 카메라로 정지 상태를 렌더한 쌍둥이 데이터셋**에 학습한 모델(움직임 뺀 것)을 대서 비교(`gs_train --eval-rest`).

→ 좋아지긴 하지만 폭이 작아짐(움직임 추정 오차 2.03 → 1.65 cm). 큰 움직임은 사진 한 장씩으로는 정하기 어렵다는 예상과 맞음.

- 그림으로 보면 차이가 큼: 보정 없음은 머리·헤드폰·머리카락·손이 두 겹으로 흐림, 보정하면 선명.
- 평균 0 규제가 없으면 모델이 "처음 자리 잡은 자세"로 남아 정지 정답과 어긋남(제어점별 평균 차이 0.21 cm → 규제 후 0.05 cm), 정지 비교 +1.8 dB.
- 정지 상태 데이터에 켜도 손해 작음: 41.10 → 40.82 dB, 머리 32.93 → 32.82 dB (보정값 평균 0.2 cm). → 직접 찍은 스캔(마스크 있을 때)에서 기본으로 켬.
- 비용(lavapipe): train_step 1.5 → 11 ms, 한 걸음 전체로는 약 2% (나머지는 그대로). 제어점 그래디언트는 따로 만든 셰이더(train_step_motion)에서만 합해, 끈 경우 공유 메모리 부담 없음.
- 아직 남은 차이(상한 41.1 vs 37~38 dB, 머리 32.9 vs 27.6~29.2 dB): 제어점 위치 움직임 추정 오차가 평균 1.10 → 0.80 cm로 줄었지만 머리는 2.0 → 1.3 cm. 한 사진에서 안 보이는 쪽 제어점과 시선 방향 움직임은 사진 한 장으로 정하기 어려움.

## bucket 상태 버퍼 둘로 나누기 (v0.8.1)

v0.8.0 Fold6 실측(140장, 960×540, 빠름): 역전파 실측 `bucket 1e30` → serial_cut 44~60 ms/회(한 회 ~80 ms의 대부분). 끝 쌍 수 68만. bucket 상태를 쌍 버퍼 용량(가장 많았던 쌍 × 1.125 × 1.25)만큼 잡아 (n/32 + 타일) × 4 KB가 128 MB를 넘었음. 실제 단계에 필요한 크기는 약 95 MB.

- 상태를 **버퍼 두 개**(각각 바인딩 한도까지)에 나눠 저장: train_forward가 bucket 번호 < limits.z면 첫 버퍼, 아니면 둘째에. 540p에서 약 190만 쌍까지.
- bucket을 쓸지는 **가장 많았던 쌍 × 1.125 ≤ 상태가 덮는 쌍 수**로 판단(쌍 버퍼의 1.25배 여유분은 빼고).
- 단계별 보호: 상태가 덮는 쌍보다 많은 단계는 갱신을 건너뜀(limits.w, train_pair_sum·step·step_sh), forward는 범위 밖 상태를 쓰지 않고 그 타일을 목록에서 뺌. 한 단계씩 돌 때는 bucket 없이 다시 돌리고, 묶음에서는 건너뛴 단계로 셈.
- 테스트: 상태 2×7 bucket(32쌍)인데 284쌍 단계 → 다시 돌아 serial_cut과 그래디언트 완전히 같음. 2×12 bucket(352쌍) → 뒤쪽 타일이 둘째 버퍼에 저장되고 serial_cut과 차이 1.2e-9(반올림).
- PC(움직이는 body, 1500회, 움직임 보정)에서 버퍼당 한도를 6 MB로 줄이면 1000회까지 bucket, 그 뒤 쌍이 늘어 덮지 못하자 serial_cut으로 넘어감; 3 MB면 처음부터 serial_cut. 둘 다 건너뛴 단계 0, 정지 비교 36.73 / 37.00 dB(한도 없음 36.96 dB).

## 화질을 막는 원인 찾기 (v0.9.0, PC lavapipe)

실제 스캔(Fold6, v0.8.1): 검증 31.2 dB · 머리 24.0 dB, **학습 사진 PSNR도 30~32 dB**에서 멈춤(가상 데이터는 ~40 dB). 학습 사진조차 못 맞춘다 = 모델 용량보다 **사진끼리 서로 안 맞는 것**(일관성)이 원인일 가능성이 큼. 후보: 카메라 자동 노출·화이트 밸런스(ARCore는 끌 수 없음), 인물 마스크 경계 흔들림(ML Kit은 내부 256 해상도), 움직임·포즈(이미 보정), 흐린 사진.

**진단 기능**(`gs::diagnose`, 앱 학습 요약 `진단 ·` 줄, `gs_train --diagnose`): 학습 끝에 모든 사진을 그 카메라(위치 보정·움직임 반영)로 렌더해 사진(× 마스크, 밝기 보정 시 그 게인으로 나눈 것)과 비교.
- 사진별 밝기 게인(사람 안쪽, 경계 3 px 밖, 둘 다 불투명한 픽셀에서 사진 = g × 렌더 최소제곱)의 분포, 색조(R/G·B/G) 차이, 사진마다 게인·오프셋을 맞췄을 때 안쪽 PSNR이 얼마나 오르는지.
- 오차가 어디 있는지: 마스크 경계 ±3 px / 윤곽 불일치(렌더와 마스크가 사람인지 아닌지 다름) / 사람 안쪽(그중 머리) / 배경.
- 흐린 사진 비율(사람 안쪽 라플라시안 분산이 중간값의 절반 미만), 가장 안 맞는 사진 3장.

가상 데이터(body 정지, 90장, 270×480, 1500회)로 확인:

| 데이터 | 검증 PSNR | 머리 | 진단: 밝기 게인 (표준편차) | 맞추면 안쪽 PSNR | 오차 위치 |
|---|---|---|---|---|---|
| 깨끗함 | 41.20 dB | 33.01 dB | 0.995~1.001 (0.2%) | 37.25 → 37.33 | 경계 85%, 안쪽 15% |
| 노출·화이트 밸런스 변화 (밝기 ±12%, R/B ±4%) | 40.64 dB | 32.79 dB | 0.965~1.020 (1.8%) | 35.45 → 36.78 | 경계 79%, 안쪽 21% |
| 마스크 경계 흔들림 (사진마다 ±4 px 침식/팽창 + 흐림) | **31.18 dB** | **23.86 dB** | 0.990~0.995 (0.2%) | 35.29 → 35.60 | **경계 96%** |

- 깨끗한 데이터도 오차의 85%가 마스크 경계 ±3 px(화면의 6%)에 있음 → PSNR은 경계에 크게 좌우됨.
- **마스크 흔들림이 실제 스캔 숫자(31.2 / 24.0 dB)를 거의 그대로 재현.** 깨끗한 마스크로 평가하면 그 모델은 36.12 dB(머리 30.76) → 숫자의 일부는 평가 마스크 자체의 잡음이지만, 모델도 실제로 5 dB 나빠짐(경계 번짐, 안쪽 −1.7 dB).
- 노출 변화는 생각보다 손해가 작음(−0.6 dB): 방향과 함께 바뀌어서 일부를 SH(보는 방향별 색)가 흡수 → 대신 뷰어에서 돌릴 때 색이 바뀌는 문제로 남음.

**밝기·색 보정**(`refine_exposure`): 사진마다 채널별 게인, forward에서 모델이 불투명한 곳의 Σ렌더², Σ렌더×사진을 타일별로 모아 닫힌 식으로 구해 0.3씩 섞음(300회×비율부터). 게인의 기하평균을 1로 고정(안 하면 모델 밝기와 게인이 서로 쫓아감). 검증 사진은 앞뒤 사진의 게인을 이어서 씀.

| 데이터 | 보정 없음 | **밝기·색 보정** |
|---|---|---|
| 노출 변화 | 40.64 dB (머리 32.79) | **41.16 dB** (32.99) — 깨끗한 데이터 수준 |
| 깨끗함 | 41.20 dB | 41.14 dB (손해 없음) |

- 배운 게인 0.931~1.051, 남은 게인 차이 1.8% → 0.1%. 테스트: 한 장을 (0.8, 0.85, 0.9)로 어둡게 하면 게인 비율이 2% 안으로 맞음.

**마스크 경계 무시(실패)**: 사진마다 마스크 경계 ±r px의 오차를 빼 봄 → 흔들리는 마스크에서 정지 정답 비교 36.12 → 33.67 dB(r = 짧은 변 1%), 32.17 dB(2%); 깨끗한 마스크에서도 41.20 → 37.36 dB. 경계를 아무도 안 잡아 주니 그 띠에 반투명 가우시안이 퍼짐. 코드에서 뺌.
