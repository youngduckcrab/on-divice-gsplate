# 온디바이스 Gaussian Splatting 앱 (Android) — 개발 계획서

| 항목 | 내용 |
|---|---|
| 문서 버전 | v0.5 |
| 작성일 | 2026-10-30 |
| 대상 플랫폼 | Android (arm64) |
| 테스트 기기 | **Galaxy Z Fold6** — Snapdragon 8 Gen 3 for Galaxy (GPU: Adreno 750), RAM 12 GB |

| 진행 방식 | Claude가 구현 → APK 배포 → 사용자가 설치·실험 → **이 대화로 피드백** → 반복 |

### 변경 이력
- v0.5: M3 1차 구현 반영 — atomic-free 그래디언트 방식 (c) 채택, densify를 M3로 앞당김(3DGS 방식, GPU에서 free list로 처리), D-SSIM은 M4로, 학습 이미지는 매 단계 업로드(128 MB 바인딩 제한 회피). §5.3 갱신.
- v0.4: 카메라와 촬영 인원이 당분간 없음 → M2(촬영) 보류, M3(학습)을 [가상 촬영 데이터셋](datasets.md)으로 먼저 진행. M3에 데이터셋 불러오기 추가, 표준 장면에 가상 촬영 3종 추가.
- v0.3: M0 기기 진단 결과 반영 ([결과](experiments/m0-fold6.md)) — float atomic 미지원에 따른 그래디언트 누적 방식, 128 MB 바인딩 제한, 1080p 촬영, 정렬 속도 목표, 메모리 예산 갱신.
- v0.2: 테스트 기기(Fold6), 촬영 대상(사람), 피드백 채널(대화), private 저장소 결정 반영. 인물 스캔 설계(§5.8) 추가, 표준 장면·리스크·마일스톤 갱신.
- v0.1: 초안.

## 1. 개요

### 1.1 목표

한 사람이 가만히 서 있거나 앉아 있는 동안 다른 사람이 폰을 들고 주위를 한 바퀴 돌며 30~60초 촬영하면, 서버 없이 **폰 안에서** 수 분 이내에 그 사람의 3D Gaussian Splatting(3DGS) 모델을 학습하고, 바로 돌려보며 확인할 수 있는 안드로이드 앱을 만든다.

레퍼런스는 Niantic의 **Scaniverse**다. Scaniverse는 AR 프레임워크의 카메라 포즈를 이용해 촬영하고, 학습을 기기 안에서 수행하며, iOS 기준 처리 시간은 약 1분 내외로 알려져 있다.

### 1.2 범위

**포함**
- ARCore 기반 촬영 (이미지 + 6DoF 카메라 포즈 + 깊이)
- 온디바이스 3DGS 학습 (Vulkan compute)
- 온디바이스 실시간 뷰어
- PLY / SPZ 내보내기 및 공유
- 실험용 기능: 학습 파라미터 조절, 성능 계측, 진단 리포트 내보내기

**제외 (현 단계)**
- iOS, 서버/클라우드 학습
- Play 스토어 배포 (APK 직접 설치로 진행)
- 메쉬 추출, 동적 장면, 건물 단위 대규모 장면
- ARCore 미지원 기기 (추후 온디바이스 SfM 경로로 검토)

### 1.3 성공 기준

> 아래 수치는 **초기 가설**이다. M0 기기 벤치마크와 M3 실측 결과로 재조정한다.

| 지표 | 1차 목표 (M3~M4) | 최종 목표 (M5~M7) |
|---|---|---|
| 촬영 시간 (피사체가 정지해 있어야 하므로 짧을수록 좋음) | 30~60초 | 20~40초 |
| 학습 시간 (촬영 종료 → 결과 확인) | ≤ 5분 | **≤ 2분** (Scaniverse급) |
| 화질 (hold-out 프레임, 인물 영역 PSNR) | ≥ 22 dB | ≥ 25 dB |
| 얼굴 품질 | 얼굴이 알아볼 수 있게 재구성됨 | 얼굴 영역에 눈에 띄는 흐림·이중상 없음 |
| 뷰어 프레임레이트 | ≥ 30 fps @ 가우시안 30만 개 | ≥ 60 fps @ 가우시안 50만 개 |
| 학습 중 최대 메모리 | < 3 GB | < 2 GB |
| 결과 파일 크기 (SPZ) | — | < 20 MB |
| 안정성 | 표준 장면 3종 학습 완료 | 표준 시나리오에서 크래시·GPU 디바이스 로스트 0회 |

## 2. 진행 방식: 빌드 → 설치 → 피드백 루프

### 2.1 사이클

```
 ┌───────────── Claude ─────────────┐         ┌───────────── 사용자 ─────────────┐
 │ 1. 마일스톤 기능 구현             │         │ 4. 폰에서 APK 다운로드·설치       │
 │ 2. CI: 빌드 + 단위 테스트 +       │ ──────► │ 5. 릴리즈 노트의 체크리스트 수행   │
 │    GPU 커널 정합성 테스트          │         │ 6. 결과·스크린샷·진단 패키지를     │
 │ 3. GitHub Release에 APK 게시      │ ◄────── │    피드백 (Issue 또는 대화)        │
 │ 7. 피드백 분석 → 수정 / 다음 단계 │         └──────────────────────────────────┘
 └──────────────────────────────────┘
```

### 2.2 APK 배포

- **GitHub Actions**: push마다 APK 빌드와 테스트를 돌린다. `version.properties`의 버전(`v0.X.Y`)에 해당하는 Release가 아직 없으면 자동으로 만들고 APK와 릴리즈 노트(`docs/releases/v0.X.Y.md`)를 첨부한다. 사용자에게 보낼 빌드는 버전을 올려서 구분한다.
- 파일명은 `gsplat-v0.X.Y.apk`. 앱 화면 상단에 버전과 커밋 해시를 표시한다.
- **서명 키 고정**: 실험용 고정 키스토어를 저장소에 포함한다. 새 버전을 기존 앱 위에 덮어 설치할 수 있어서 매번 삭제할 필요가 없고 스캔 데이터도 유지된다. (공개 배포용 키가 아님. 저장소는 private)
- **설치 방법**: 폰 브라우저에서 GitHub에 로그인 → 저장소의 Releases → 최신 버전의 APK 다운로드 → "출처를 알 수 없는 앱 설치" 허용.
- private 저장소의 Actions는 계정의 무료 분(월 한도)을 쓴다. 빌드 1회당 수 분 수준이라 이 프로젝트 규모에서는 충분하다.

### 2.3 피드백 방법

매 릴리즈 노트에 **변경 사항 / 테스트 체크리스트 / 알려진 문제**를 적는다. 피드백은 **이 대화**로 받는다. 사용자는 아래 양식을 채워 붙여 넣고, 스크린샷은 이미지로 첨부한다.

```
버전: v0.X.Y (앱 정보 화면의 커밋 해시)
기기: 모델명 / Android 버전
체크리스트: 1 ✅  2 ❌  3 ✅ ...
문제: 무엇을 했을 때 → 무엇이 일어났는지 (스크린샷·화면녹화 첨부)
수치: 앱이 표시한 학습 시간 / FPS / PSNR 등
첨부: 진단 패키지 zip
의견: 자유롭게
```

- **"요약 복사" 버튼**: 앱이 진단·학습 결과를 대화에 바로 붙여 넣을 수 있는 짧은 텍스트로 만들어 클립보드에 복사한다. 이것이 기본 피드백 수단이다.
- **전체 JSON 복사/공유**: 더 자세한 정보가 필요할 때 기기·GPU 정보 전체, 학습 지표(손실·PSNR·단계별 시간·온도), 사용한 파라미터, 카메라 궤적을 텍스트로 내보낸다.
- **스캔 데이터셋 전체 내보내기** (필요할 때만): nerfstudio `transforms.json` 형식. PC에서 gsplat / nerfstudio / Brush로도 학습해 결과를 비교할 수 있다.
- **개인정보**: 촬영 대상이 사람이므로 앱이 만드는 요약·JSON에는 **사진을 넣지 않는다**. 얼굴이 담긴 스크린샷이나 데이터셋은 사용자가 공유 여부를 직접 고른다. 촬영되는 사람에게는 미리 동의를 받는다.

### 2.4 역할 분담과 한계

| | 가능 | 불가능 |
|---|---|---|
| Claude | 빌드, 단위 테스트, **소프트웨어 Vulkan(Mesa lavapipe)으로 GPU 커널 정합성 테스트** (CPU 레퍼런스 구현과 forward/backward 수치 비교), 사용자 데이터셋으로 엔진의 Linux 빌드 재현 (느리지만 결정적) | 실제 기기에서의 실행, 성능·발열 측정, ARCore 동작 확인, 기기 드라이버 버그 확인 |
| 사용자 | 실제 기기 테스트, 촬영, 체감 품질 평가 | — |

그래서 엔진은 처음부터 **Android와 Linux에서 함께 빌드되는 C++ 코드**로 작성하고, 모든 단계에 계측을 넣는다.

## 3. 배경 조사와 시사점

| 레퍼런스 | 내용 | 시사점 |
|---|---|---|
| **Scaniverse** (Niantic) | AR 프레임워크 포즈 기반 촬영 → 온디바이스 학습. iOS에서 처리 약 1분 내외. 내부 구현은 비공개 | 목표 지점. 무거운 SfM을 생략하고 AR 포즈를 그대로 쓰는 것이 속도의 핵심으로 추정 |
| **PocketGS** (arXiv 2601.17354, 2026) | 모바일 온디바이스 3DGS 학습 논문. 정보량 기반 프레임 선별 + GPU BA + MVS로 기하 prior 구성, Adam 업데이트를 단일 fused kernel로 처리. iPhone 15에서 500 iteration ≈ 4분, 피크 메모리 < 3 GB 보고 | 좋은 초기화로 iteration 수를 줄이는 것이 핵심. fused optimizer. 메모리 예산의 근거 |
| **Brush** (Rust, Burn + wgpu) | 크로스플랫폼 3DGS 학습·뷰어, Android 지원(실험적). WebGPU에 float atomic이 없어 CAS loop로 에뮬레이션 | Android GPU에서 학습이 가능함을 보여줌. 커널 구조 참고 + 같은 기기 성능 기준선 |
| **gsplat** (nerfstudio, Apache-2.0) | CUDA 3DGS 라이브러리. 수식과 backward가 깔끔하게 정리됨 | 래스터라이저 수식의 주 레퍼런스 |
| **원본 3DGS** (Inria) | 비상업 라이선스 | 코드는 가져오지 않고 논문 수식만 참고 |
| **3DGS-MCMC, Taming 3DGS** | 가우시안 개수 예산을 고정한 densification | 모바일에서 메모리가 예측 가능 → 채택 후보 |
| **FastGS** (CVPR 2026) | 데스크톱에서 약 100초 학습. 다중 시점 일관성 기반 densify/prune | 적은 iteration에서의 densification 전략 참고 |
| **SPZ** (Niantic, MIT) | Scaniverse의 압축 포맷, PLY 대비 약 90% 작음 | 내보내기 포맷으로 채택 |

**핵심 시사점**
1. **SfM(COLMAP) 생략** — ARCore 포즈와 깊이를 그대로 써서 전처리 시간을 거의 0으로 만든다.
2. **좋은 초기화 = 적은 iteration** — ARCore Depth로 조밀한 포인트 클라우드를 만들어 초기화한다.
3. **고정 예산** — 가우시안 수 상한, 낮은 학습 해상도, 낮은 SH 차수로 시작해 점진적으로 올린다.
4. **모바일 GPU 특성 대응** — 메모리 대역폭이 데스크톱의 1/10~1/15 수준이므로 커널 fusion, fp16, sparse 업데이트가 중요하다.

## 4. 시스템 아키텍처

### 4.1 전체 파이프라인

```
[촬영]   ARCore 세션 — 프레임마다 이미지, 카메라 포즈, intrinsics, depth + confidence, 추적 상태
           │  키프레임 선택 (이동량 · 회전량 · 선명도 · 추적 품질)
           ▼
[저장]   scans/<id>/  images/*.jpg, depth/*.bin, frames.json (포즈·intrinsics), meta.json
           ▼
[초기화] depth 역투영 → 월드 좌표 포인트 → voxel 병합 → 색 · 크기 · 불투명도 초기값
           ▼
[학습]   Vulkan compute: 전처리 → 정렬 → forward 래스터 → loss → backward → Adam → (densify/prune)
           │  실시간 미리보기, 손실 / PSNR 그래프, 단계별 시간 · 온도 계측
           ▼
[결과]   뷰어 (Vulkan graphics)  ·  PLY / SPZ 내보내기  ·  공유
```

### 4.2 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| UI | Kotlin + Jetpack Compose | 표준 스택, 화면 구성이 빠름 |
| 촬영 | ARCore SDK (Kotlin API) + OpenGL ES 카메라 프리뷰 | 6DoF 포즈와 깊이를 바로 얻을 수 있음. ARCore 카메라 텍스처가 GLES 기반이라 공식 샘플 구조를 따름 |
| 엔진 | C++20 + Vulkan 1.1 (NDK, CMake) | 모바일 GPU를 가장 세밀하게 제어(subgroup, fp16, 메모리). Linux에서 같은 코드로 테스트 가능 |
| 셰이더 | GLSL → SPIR-V (빌드 시 glslc) | NDK에 포함된 툴체인 |
| 라이브러리 | VMA (MIT), glm (MIT), libspz (MIT), stb (public domain) | 라이선스가 단순 |
| CI | GitHub Actions (Android 빌드 + Linux/lavapipe 테스트) | 기기 없이 자동 검증 |
| 최소 사양 | Android 10 (API 29) 이상, arm64, ARCore 지원 기기, Vulkan 1.1 | 열 관리 API 등 상위 API는 런타임에 확인 후 사용 |

**엔진 구현 방식 비교 — 결정: A안**

| 안 | 장점 | 단점 |
|---|---|---|
| **A. 자체 C++/Vulkan 엔진** | 최대 성능과 제어권, 앱 통합이 단순(JNI), lavapipe로 CI 테스트 가능 | 구현량이 가장 많고 드라이버 차이를 직접 대응해야 함 |
| B. Brush(Rust/wgpu) 포크·임베드 | 동작하는 학습기를 빨리 확보 | wgpu 추상화 때문에 모바일 최적화에 한계(float atomic 없음 등), Rust + Burn 빌드 체인 추가, 촬영 파이프라인과의 통합 비용 |
| C. ExecuTorch / MNN 등 모바일 ML 런타임 | 익숙한 ML 스택 | 미분 가능한 래스터라이저를 결국 커스텀 op로 직접 작성해야 하고, 학습 지원이 미흡 |

A안으로 구현하고, Brush는 커널 구조 참고와 (필요하면) 같은 기기에서의 성능 기준선으로 활용한다.

### 4.4 데이터 포맷과 좌표계

- **스캔 폴더**: 4.1의 구조. `frames.json`에 프레임별 `timestamp, pose (4×4 camera-to-world), fx, fy, cx, cy, width, height, tracking_state, sharpness`를 저장한다.
- **좌표계**: ARCore 월드 좌표(오른손 좌표계, +Y가 중력 반대 방향, 미터 단위). ARCore 카메라는 OpenGL 관례(−Z가 전방)이고, 엔진 내부는 OpenCV 관례(+Z가 전방)로 변환해서 쓴다. 변환은 한 곳에서만 처리한다.
- **이미지와 포즈의 짝**: CPU 이미지는 센서 방향(가로) 기준이므로 `Camera.getImageIntrinsics()`와 디스플레이 회전이 적용되지 않은 `Camera.getPose()`를 짝지어 쓴다. M2에서 depth 재투영 테스트로 검증한다.
- **내보내기**: nerfstudio `transforms.json` (OpenGL 관례 camera-to-world) — PC 도구와 호환.

## 5. 핵심 컴포넌트 설계

### 5.1 촬영 (ARCore)

- **세션 설정**
  - 깊이: 지원 기기면 Raw Depth(+confidence) 사용, 미지원이면 특징점만 사용
  - 포커스 고정 시도 (초점 변화로 intrinsics가 흔들리는 것 방지)
  - CPU 이미지 해상도: 기본은 640×480. `Session.getSupportedCameraConfigs()`에서 가장 높은 해상도를 고른다. **Fold6은 1920×1080 @30fps 지원 확인(M0)** → 1080p로 저장, 학습은 960×540부터
- **키프레임 선택**
  - 추적 상태가 `TRACKING`인 프레임만 사용
  - 직전 키프레임 대비 이동량이 장면 깊이의 약 5% 이상이거나 회전 5~10° 이상일 때 채택
  - 선명도: Y 채널 Laplacian 분산이 최근 중앙값보다 크게 낮으면 제외. 포즈 차분으로 각속도를 구해 너무 빠르면 제외
  - 최대 키프레임 수 제한 (기본 150~250, 실험 파라미터로 노출)
- **촬영 가이드 UI**: 추적 상태, 키프레임 수, 속도·조도 경고, (물체 모드) 대상 주변 커버리지 표시
- **저장**: JPEG 인코딩은 백그라운드 스레드에서. depth / confidence 원본, ARCore 특징점도 함께 저장
- **후순위 고급 기능**: Shared Camera(Camera2)로 고해상도 프레임 획득, ARCore Recording(MP4)으로 세션을 기록해 두고 키프레임 설정만 바꿔 재처리

### 5.2 초기화

- 각 키프레임의 raw depth를 confidence 임계값으로 거른 뒤 월드 좌표로 역투영하고, voxel grid로 병합한다 (평균 색, 관측 횟수 누적). 여러 시점에서 반복 관측된 점만 남긴다.
- 초기값: scale = 이웃 점 간 거리(또는 voxel 크기), rotation = identity, opacity = 0.1~0.5, SH DC = 픽셀 색.
- **Depth 미지원 기기**: ARCore 특징점을 누적하고 장면 범위 안에 랜덤 점을 보충한다 (품질·속도 저하 예상).
- (M6) PocketGS처럼 다중 시점 일관성 검사나 경량 MVS로 prior 품질을 높이는 방안을 검토한다.

### 5.3 학습 엔진 (Vulkan compute)

**iteration 1회의 흐름** (v0.3.0 구현, `engine/src/trainer.cpp`, `engine/shaders/train_*.comp`)

1. **전처리** (`train_project`) — scale·quaternion으로 3D 공분산 → EWA 투영으로 2D conic → SH에서 색. 타일은 opacity를 반영한 타원(alpha ≥ 1/255인 영역)이 실제로 닿는 것만 센다(v0.3.9, 행마다 타원의 x 범위를 구함; 그 전에는 가장 긴 축 반경의 원을 감싼 사각형). 타일 수를 prefix sum으로 합산(`scan_local` → `radix_scan` → `scan_add`).
2. **정렬** (`train_emit` → radix sort → `train_ranges`) — 키 = (타일 ID << 16) | 16-bit log 깊이. 32-bit 키만 쓰므로 `shaderInt64` 불필요. 정렬 값은 정렬 전 쌍 인덱스.
   - 기기마다 subgroup 크기가 16~128로 다르므로 이에 의존하지 않는 radix sort를 쓴다. GPU 간 forward-progress 보장이 필요한 onesweep 방식은 쓰지 않는다.
   - 쌍 개수는 매 단계 CPU로 읽어 온다(제출 2회/단계). 간접 dispatch로 없애는 것은 M5.
3. **Forward 래스터** (`train_forward`) — 16×16 타일, 픽셀별 front-to-back alpha blending. 최종 투과율과 마지막 기여 인덱스, 픽셀별 dL/dC, 타일별 loss 합을 저장한다.
4. **Loss** — L1. 마스크가 있으면 정답을 무작위 배경색 위에 합성하고 렌더도 같은 배경색 위에 그려, 대상 밖은 투명해지도록 학습한다. (M4: (1−λ)·L1 + λ·D-SSIM)
5. **Backward 래스터** (`train_backward`) — back-to-front로 다시 순회. **(c) atomic-free 방식 채택**: 가우시안 B개씩 묶어 픽셀별 그래디언트를 subgroupAdd → 공유 메모리에서 subgroup끼리 합산 → (타일, 가우시안) 쌍별 그래디언트를 정렬 전 인덱스 위치에 기록. 가장 작은 subgroup 크기에 맞춰 공유 메모리 크기를 specialization constant로 정한다 (Adreno 64 → B=32, lavapipe 8 → B=8).
   - (a)는 Fold6에서 불가(float atomic 없음), (b)·(d)는 (c)가 느릴 때 비교 후보로 남긴다.
   - **v0.3.11**: 시작 검증을 bucket·serial_cut 확인 + 긴 목록 일치 확인으로 줄이고 검증용 학습기를 장면 크기로 할당(이전엔 가우시안 30만 개분). 최적화를 쌍 합 / 기하 / SH(계수 float당 스레드 하나, 연속 메모리 접근)로 분리. 정렬과 타일 범위를 GPU가 계산한 크기로 간접 dispatch. Vulkan 검증 레이어로 테스트.
   - **v0.3.10**: 스플랫별 역전파(bucket/bucket2, Taming 3DGS 방식) — 순전파가 스플랫 32개마다 픽셀 상태(T, 앞쪽 색)를 저장하고, 역전파는 스레드가 스플랫 하나씩 맡아 타일 픽셀을 순서대로 훑으며 상태를 다음 스레드로 넘김(공유 메모리, 단계마다 barrier 1번). 픽셀 합산 단계가 사라짐. PC body에서 역전파 ~45% 단축. 쌍 개수를 GPU에서 바로 써서 1회 안의 CPU 대기 제거, 10회를 한 번에 제출, 디스크립터 셋 재사용. 다음 후보: 최적화 단계의 가우시안별 쌍 합산(부하 불균형), 렌더.
   - **v0.3.9**: 학습 중 실측 재선택 — 그래디언트가 맞는 변형들을 같은 실제 학습 단계에서 번갈아(A B C C B A) 재고 가장 빠른 것으로 전환(20회째, 이후 500회마다). 시작 전 합성 벤치마크(12k 가우시안)는 첫 선택에만 쓴다. 타원 타일 판정으로 쌍 감소(project와 emit이 `precise` 연산으로 같은 결과를 내고, 어긋나면 빈 타일로 채워 세어 보고).
   - **v0.3.8**: subgroup_lane4/lane1(subgroup 번호·elect·벡터 덧셈 없이 스칼라 subgroupAdd) — Fold6에서 처음으로 컴파일·그래디언트 정상, 하지만 13~14 ms로 serial_cut(8.9 ms)보다 느림. 같은 코드인데 실행마다 모든 단계가 ~1.7배 차이 → GPU 클럭 상태.
   - **v0.3.7**: 그래디언트가 맞는 변형들을 폰에서 벤치마크해 가장 빠른 것 선택 → serial_cut, 빠름 105 → 75 s.
   - **v0.3.6**: 역전파 serial_cut2(타일별 마지막 기여 지점에서 멈춤 + barrier 1회당 가우시안 2개) — PC에서 역전파 25~35% 단축, 결과 동일. 제출별 벽시계/GPU 시간 측정, subgroup 조합 probe. 실측: [m3-fold6.md](../experiments/m3-fold6.md).
   - **v0.3.5 Fold6 자가 검사 — 학습 동작 확인**: serial 역전파의 그래디언트가 CPU 기준과 일치(일반·마스크 모두, 0 아닌 쌍 28/36 = PC와 동일), 장면 맞추기 24.9 → 36.5 dB(600회, 2.3 ms/회, PC 36.8 dB). shared는 여전히 0. subgroup 기능은 하나씩(basic/elect/id/float add/ballot)은 모두 컴파일되지만 조합한 probe와 학습 셰이더는 실패 → 다음: 조합(vec4 덧셈, id+add 등) probe로 원인 찾아 빠른 역전파 복구.
   - **v0.3.4 Fold6 자가 검사**: 공유 메모리 atomic 정상, 순전파 기록·갱신 단계 정상, shared 역전파 출력만 거의 전부 0(36쌍 중 1쌍). subgroup은 최소 probe 셰이더도 `VK_ERROR_UNKNOWN`. → v0.3.5: 순전파와 같은 구조(단일 반복문, 가우시안 하나씩, 2단계 공유 메모리 합)의 serial 역전파 추가, 학습 전 폰 GPU에서 변형별 그래디언트를 CPU 기준과 비교해 맞는 첫 변형을 선택(없으면 학습 거부), subgroup 기능별 컴파일 probe.
   - **v0.3.3 Fold6 자가 검사**: 순전파는 CPU 기준과 일치(이미지 차 0.002, loss 일치)하지만 shared 역전파의 그래디언트가 전부 0 → 학습이 전혀 진행되지 않음(장면 맞추기 24.9 → 24.9 dB). subgroup 역전파는 vote·특수 상수 없이도 `VK_ERROR_UNKNOWN`. 유력 원인: 타일의 기여 수 최댓값을 구하던 공유 메모리 `atomicMax`(radix sort가 쓰는 atomicAdd는 정상) → v0.3.4에서 트리 최댓값으로 대체, 스칼라 subgroupAdd 버전 추가, GPU 기본 연산 probe와 단계별(순전파 기록 → 역전파 출력 → 갱신) 검사 추가. shared 역전파는 1회 214 ms 중 173 ms로 매우 느림.
   - **v0.3.1 Fold6 결과**: 학습은 돌았으나 lizard 결과가 "색이 사라지고 흰색만 조금". 원인: 점 구름(3만 개, 조각상 반경 3 m)이 거의 조각상 위에만 있어 공원 배경을 학습할 수 없었음 → 주변까지 6만 개로 다시 뽑아 90×160·600회 hold-out PSNR 15.5 → 24.1 dB. opacity 리셋은 짧은 학습에서 이득이 없고(head 36.1 → 36.5 dB, lizard 15.5 → 15.1 dB) 중간에 모델이 사라지는 것처럼 보여 기본값에서 뺌.
   - **v0.3.0 Fold6 결과**: 학습 파이프라인 생성이 `VK_ERROR_UNKNOWN`으로 실패. 공유 메모리 배열 크기에 specialization constant 식(`OpSpecConstantOp`)을 쓴 셰이더가 원인으로 추정 → v0.3.1에서 고정 크기 + push constant로 바꾸고, subgroup 없이 공유 메모리 트리로 합산하는 대체 셰이더를 두어 subgroup 버전이 거부되면 자동 전환. 실패 시 셰이더 이름을 모두 보고.
6. **Backward 전처리 + Adam** (`train_step`, 가우시안당 1스레드) — 정렬 전 순서에서 연속인 자기 쌍들을 합산 → 투영 · SH(시점 방향 포함) · 공분산 · quaternion 정규화를 거쳐 3D 파라미터 그래디언트 → fused Adam. 위치 학습률은 카메라 범위 기준 지수 감쇠. densify 통계(NDC 위치 그래디언트 크기, 보인 횟수, 최대 반경)도 여기서 누적.
7. **Densify / Prune** (`train_densify_mark`, `train_densify_spawn`) — 3DGS 기본 방식: 평균 위치 그래디언트가 임계값 이상이면 작은 것은 복제, 큰 것은 분할(1.6배 축소, 가우시안 분포에서 표본), opacity < 0.005나 너무 큰 것은 제거. 제거된 슬롯은 free list로 재사용하고 슬롯 상한(가우시안 예산)을 넘지 않는다. 정수 atomic만 쓴다. opacity 리셋도 GPU에서.
   - 3DGS-MCMC 재배치, Taming식 점수 기반 방식은 M4에서 비교.

**검증**: CI(lavapipe)에서 CPU 배정밀도 기준 구현과 forward 이미지, 모든 파라미터 그래디언트(위치, scale, rotation, opacity, SH 0~3차, 마스크 유무)를 중앙 차분으로 비교한다 (상대 오차 ~1e-9). 알려진 장면을 다시 맞추는 종단 테스트도 함께 돈다.

**점진 스케줄**: SH 0차 → 3차 (기본 3000회 기준 500회마다 1차씩, 학습 횟수에 비례해 조정). 학습 해상도 단계적 증가는 M4 후보.

**메모리 예산** (가우시안 1개당)
- 파라미터는 SH 1차 기준 23 float(약 92 B). 그래디언트와 Adam 모멘트 2개까지 포함하면 약 0.4 KB. SH 3차면 약 1 KB.
- 가우시안 30만 개 → 120~300 MB. 여기에 타일 쌍·정렬 버퍼 수십~100 MB, 학습 이미지(200장 × 640×480 RGBA ≈ 245 MB).
- **전체 1 GB 안팎**을 목표로 한다 (M0에서 측정 시 가용 RAM 1.8 GB → 상한 1.5 GB).
- **바인딩 제한**: Adreno 750은 storage buffer 바인딩 1개가 최대 128 MB. 학습 이미지는 CPU 메모리에 두고 매 단계 현재 이미지만 올린다(360×640이면 0.9 MB). 쌍별 그래디언트(48 B/쌍)가 이 제한에 걸리므로 쌍은 최대 약 280만 개.

**정렬 속도**: M0에서 32-bit 키 100만 개 정렬이 20.9 ms(50 Mkeys/s, 결과 정확). 학습에는 4~8배 빨라야 하므로 깊이 선정렬 + 타일 ID 키(3~4 패스), subgroup 기반 순위 계산으로 개선한다.

**안정성**: Android GPU 드라이버는 너무 긴 dispatch를 멈춤으로 판단해 `VK_ERROR_DEVICE_LOST`를 낼 수 있다. dispatch를 짧게 나누고, 학습 중 UI 미리보기는 낮은 빈도로 그린다.

### 5.4 뷰어

- Vulkan graphics 파이프라인: 가우시안마다 인스턴스 쿼드를 그리고, 프래그먼트 셰이더에서 2D 가우시안을 평가한다. premultiplied alpha blending.
- 정렬: 학습기와 같은 GPU radix sort. 카메라가 크게 움직였을 때만 다시 정렬하는 옵션.
- 렌더링용 데이터는 fp16으로 압축해 대역폭을 줄인다.
- 조작: 오빗 / 팬 / 줌, 시점 초기화, 학습 카메라 위치로 이동.
- HUD: FPS, 가우시안 수, GPU 시간.

- 사용 가능한 API를 런타임에 확인해 쓴다: 열 상태 리스너(API 29+), `PowerManager.getThermalHeadroom()`(API 30+), ADPF `PerformanceHintManager`(API 31+).

- v1은 학습 중 화면 켜짐을 유지한다. 이후 Foreground Service로 백그라운드 학습을 검토한다.
- 학습 시작 전에 가용 메모리를 확인해 가우시안 예산을 자동으로 정한다. OOM이나 디바이스 로스트가 나면 마지막 체크포인트에서 재개한다.

### 5.7 실험 기능 (사용자가 직접 실험하는 부분)

- **학습 프리셋**: 빠름 / 균형 / 고품질
- **고급 설정**: iteration 수, 해상도 스케줄, 가우시안 예산, SH 차수, densify 방식, 학습률, loss 가중치, atomic 전략, 타일 크기
- 결과마다 사용한 파라미터·기기 상태·지표를 `metrics.json`으로 함께 저장한다. 같은 스캔으로 설정만 바꿔 다시 학습하고 결과를 나란히 비교하는 화면을 제공한다.
- **벤치마크 모드**: 고정된 합성 장면으로 단계별 커널 시간을 잰다 (기기 간·버전 간 비교 기준)
- **개발자 오버레이**: 단계별 GPU 타임스탬프, 메모리, 온도

### 5.8 인물 스캔 특화 설계

사람은 물체와 달리 **완전히 정지하지 못하고**(호흡, 눈 깜빡임, 몸의 흔들림), **얼굴의 작은 오류도 크게 눈에 띈다**. 또 스캔 결과에서 원하는 것은 보통 배경이 아니라 사람이다. 이를 반영해 다음을 설계에 넣는다.

| 항목 | 설계 |
|---|---|
| 촬영 방식 | 촬영자가 피사체 주위를 1~1.5 m 거리로 한 바퀴(필요하면 높이를 바꿔 두 바퀴) 돈다. 피사체는 정지 자세 유지. 셀프 스캔은 지원하지 않음 |
| 촬영 가이드 | 피사체 위치를 기준으로 한 **원형 커버리지 표시**(방위각 구간별 채움), 거리·속도 경고, 남은 구간 안내. 짧은 촬영(20~40초)을 유도해 피사체 움직임을 줄임 |
| 추적 안정성 | ARCore 추적은 배경의 특징점에 의존한다. 민무늬 옷을 화면 가득 찍으면 추적이 흔들리므로 **배경이 함께 보이는 거리**를 유지하도록 안내 |
| 인물 분할 | 키프레임마다 온디바이스 인물 분할 마스크를 만든다 (후보: MediaPipe Image Segmenter의 selfie multiclass 모델 — 머리카락·얼굴 피부·몸·옷 구분 가능, 또는 ML Kit Selfie Segmentation). M2에서 두 가지를 비교해 선택 |
| 초기화 | depth 포인트 중 마스크 안의 점만 사용 → 인물 포인트 클라우드. 바닥 평면(ARCore plane)은 결과를 똑바로 세우는 기준으로 사용 |
| 학습 | 기본은 **인물만 학습**: 마스크 바깥은 무작위 배경색으로 바꿔 학습해 배경이 투명하게 되도록 유도. 학습할 영역과 가우시안 수가 줄어 **속도 측면에서도 유리**하다. "배경 포함" 옵션도 제공 |
| 얼굴 품질 | 얼굴 영역 검출 후 loss 가중치 상향(M4), 얼굴 영역 PSNR을 별도 지표로 기록 |
| 움직임 대응 | 다른 프레임들과 광도 일관성이 크게 어긋나는 키프레임을 자동 제외(M6). 학습 중 포즈 미세 보정이 작은 흔들림을 일부 흡수 |
| SH 차수 | 피부·옷은 시점에 따른 색 변화가 작으므로 SH 1차를 기본으로 해 메모리와 시간을 아낀다 |
| 크롭 | 마스크와 바닥 평면으로 인물 주변 영역을 자동 크롭, 사용자가 박스로 미세 조정 |
| 개인정보 | 모든 처리는 기기 안에서 수행. 피드백용 요약·JSON에는 이미지 미포함 (§2.3) |

**테스트 기기(Galaxy Z Fold6) 관련**
- GPU가 Adreno 750이므로 Adreno 경로를 1순위로 최적화한다. 실제 지원 기능(float atomic, subgroup 크기, fp16 등)은 M0 진단으로 확인한다.
- 폴더블이라 펼침·접힘에 따라 화면 크기와 비율이 바뀐다. 촬영·학습 중 화면이 바뀌어도 작업이 끊기지 않도록 화면 구성 변경을 앱이 직접 처리하고, 레이아웃은 커버 화면과 메인 화면 모두에 맞춘다.

## 6. 성능 예산 추정 (가설)

- 데스크톱 고성능 GPU에서 640×480 이미지, 가우시안 20만 개 규모의 iteration은 수 ms 수준이다. 모바일 GPU는 연산 성능이 약 1/20, 메모리 대역폭이 약 1/10~1/15이므로 **iteration당 50~120 ms**를 예상한다.
- 그러면 2분 동안 1,000~2,400 iteration을 돌릴 수 있다. PocketGS는 좋은 prior로 500 iteration에서도 쓸 만한 결과를 보고했다.
- **전략**
  1. depth 기반 초기화로 1,000~2,000 iteration 안에 수렴시킨다.
  2. 초반 iteration은 저해상도로 싸게 돌린다.
  3. 커널 최적화로 iteration 시간 자체를 줄인다.
- M0 마이크로벤치마크(정렬, 대역폭)와 M3 실측으로 이 추정치를 갱신한다.

### 진행 순서 변경 (v0.4)

카메라와 촬영을 도와줄 사람이 당분간 없으므로 **M2(촬영)는 보류**하고 **M3(학습)를 먼저** 한다. 학습 입력은 실제 촬영 대신 [가상 촬영 데이터셋](datasets.md)을 쓴다: 사람 머리 스캔(흉상), 전신 캐릭터, 실제 Scaniverse 스캔(도마뱀 조각상)을 폰으로 한 바퀴 도는 것처럼 렌더링한 180장과 정확한 카메라 포즈, 인물 마스크, ARCore와 비슷하게 만든 깊이. M2에서 만들 촬영 결과도 같은 형식(`transforms.json`)으로 저장하므로, 카메라가 생기면 학습 코드는 그대로 쓴다.

### M2 — 촬영 & 데이터셋 · 2~3 사이클 (v0.5.0에서 시작)

**v0.5.0**: 촬영 탭. ARCore(1920×1080 CPU 이미지, raw depth + 신뢰도, 초점 고정), 시작 시 화면 가운데 hit test로 피사체 위치, 키프레임 자동 선택(이동 5%·최소 3 cm 또는 회전 5°, 속도 제한, 선명도), 피사체 주위 36구간 커버리지 원, 백그라운드 저장(JPEG, 16-bit 깊이·8-bit 신뢰도 PNG, ML Kit 인물 분할 마스크 — 세운 이미지로 분할 후 센서 방향으로 되돌림), 끝나면 `transforms.json`으로 데이터셋 저장 → 학습 탭에서 바로 학습. 이미지는 센서 방향(가로) 그대로 두고 `Camera.getPose()`와 짝지어, 회전 변환 없이 포즈와 이미지가 맞게 함. 디버그 3D 뷰와 재투영 검증 도구는 아직.

**v0.6.0 (녹화하면서 처리)**: 사용자 요구 — "다 찍고 나서 사진을 나누고 누끼를 따면 그 과정이 느려서, 학습이 빨라도 소용없다." 키프레임마다 녹화 중에 변환 → 인물 분할 → **대상 고르기**(시작 때 고른 사람의 몸 중심선에 닿는 영역만, 화면에서 붙어 보이는 다른 사람은 깊이로 0.8 m 넘게 떨어진 부분 제거) → 메모리 데이터셋에 추가, 파일 쓰기는 백그라운드. [완료] 직후 메모리에서 바로 학습(빠름·표준). 화면에는 실시간 분할로 대상만 밝게 표시. 촬영 대상은 사람만(사용자 결정 2026-10-31). iPhone도 고려해 키프레임 선택·변환·대상 고르기·데이터셋·파일 쓰기를 C++ 엔진(`gs/capture.h`)으로 옮기고, 플랫폼 쪽에는 AR 프레임워크(포즈·깊이)와 인물 분할 호출만 남김.

**v0.7.0 (첫 실제 촬영 이후)**: S24 Ultra 첫 스캔(170장)이 끝까지 학습됨(메모리로 바로). 검증 25.8 dB · 머리 14.4 dB, 334 s. 원인 두 가지를 고침: (1) 초반 쌍 급증으로 bucket 역전파가 꺼진 채 끝까지 감 → 재선택 때 쌍 버퍼를 줄여 복귀, 초기화 이상점 처리(4.7 s → 1 s 이하 예상); (2) ARCore 포즈 오차 → **학습 중 카메라 포즈 보정**(사진마다 회전·이동 보정을 같은 역전파로 Adam, 검증 사진은 평가 전 맞춤). 가상 실험에서 0.8 cm 오차 35.0 → 39.7 dB, 3 cm 28.6 → 35.1 dB. 직접 찍은 스캔에서 기본 켬.

**목표**: 학습에 쓸 수 있는 품질의 이미지 + 포즈 + 깊이를 확보한다.

**구현**: ARCore 촬영 화면, 키프레임 선택, **인물 주위 원형 커버리지 가이드**, **인물 분할 마스크**(§5.8), 스캔 목록, 저장 · 내보내기, **디버그 3D 뷰** (카메라 궤적 + 마스크로 거른 인물 포인트 클라우드를 M1 뷰어로 표시), 재투영 검증 도구

**사용자 테스트**
1. 표준 장면 촬영 (§8) — 먼저 P0(정지한 대용물)로 파이프라인을 확인한 뒤 사람으로
2. 디버그 뷰에서 궤적과 포인트 클라우드가 실제와 맞는지, 마스크가 사람을 잘 따는지 (특히 머리카락 경계)
3. 촬영 가이드가 한 바퀴 도는 데 도움이 되는지, 촬영 중 끊김이나 경고가 어떻게 느껴지는지
4. (선택) 데이터셋 zip을 PC로 옮겨 nerfstudio / gsplat으로 학습 시도

**완료 기준**: 인물 포인트 클라우드가 이중상 없이 정합되고 마스크가 인물 윤곽을 따라감

### M3 — 온디바이스 학습 v1 `v0.3` · 3~5 사이클 ★ 핵심 난관

**목표**: 폰에서 처음부터 끝까지 학습되는 첫 결과.

**구현**: **데이터셋 불러오기**(zip: 이미지 + `transforms.json` + 마스크 + 깊이) 및 카메라 궤적·깊이 포인트 확인 화면, Vulkan 전처리 · 정렬 · forward · backward · Adam, L1 loss, 인물 마스크 기반 학습(배경 무작위색 치환), depth 초기화, 고정 가우시안 수(densify 없음), SH 0차, 학습 화면(미리보기, 손실/PSNR 그래프, 단계별 시간), 결과 저장 → 뷰어. CI에서 CPU 레퍼런스 대비 그래디언트 수치 검증.

**v0.3.0에서 실제로 한 것**: 위 항목 중 카메라 궤적·깊이 포인트 확인 화면은 빠졌고(학습 미리보기로 대신), 대신 densify(3DGS 방식)와 SH 3차까지를 앞당겨 넣었다. 프리셋 3개(빠름 360px·2000회 / 표준 360px·4000회 / 고품질 540px·7000회). lavapipe(CPU 소프트웨어 Vulkan)에서 head 데이터셋 180×320, 250회 학습만으로 얼굴이 알아볼 수 있게 재구성됨을 확인 — 폰 속도와 품질은 사용자 테스트로 측정한다.

**사용자 테스트**
1. 가상 촬영 데이터셋(head → lizard → body 순)으로 학습 실행 → 완료까지 걸린 시간
2. 결과를 뷰어로 확인 (스크린샷 + 학습 이미지와 비교)
3. 진단 패키지 공유 (iteration 시간, 온도, 메모리)
4. 같은 스캔으로 2회 학습 → 재현성 확인

**완료 기준**: 표준 장면이 알아볼 수 있게 재구성되고, 크래시 없이 완료되며, hold-out PSNR이 측정됨

### M4 — 품질 향상 `v0.5` · 2~3 사이클

**구현**: D-SSIM loss, 예산 고정 densification (MCMC / Taming 비교), SH 1차, 해상도 · SH 점진 스케줄, opacity 정규화, **얼굴 영역 loss 가중치와 얼굴 PSNR 지표**, 프리셋 & 고급 설정 UI, 결과 비교 화면

**사용자 테스트**: 프리셋별 시간 · PSNR · 화질 비교, 고급 설정으로 자유 실험

**완료 기준**: hold-out PSNR ≥ 22 dB, 학습 ≤ 5분

**진행**: v0.4.0 — D-SSIM(0.8 L1 + 0.2 (1 − SSIM), GPU에서 SSIM과 그래디언트, CPU 유한차분으로 검증), 프리셋 해상도 상향(빠름·표준 540×960, 고품질 720×1280), 검증 SSIM 지표, 500회마다 발열 헤드룸. 다음: 얼굴 영역 loss 가중치와 얼굴 PSNR.

### M5 — 속도 최적화 `v0.6` · 2~4 사이클

**구현**: GPU 타임스탬프 프로파일링, sparse Adam, fp16 경로, 기기별 atomic 전략 자동 선택, 타일 크기 · workgroup 튜닝, 커널 fusion, ADPF 열 관리

**사용자 테스트**: 벤치마크 모드 + 표준 장면 학습 시간, 3회 연속 학습 시 발열과 성능 저하

**완료 기준**: 학습 ≤ 2~3분, 연속 실행 시 성능 저하 < 30%

**현재 상태 (M3 중에 앞당겨 진행, v0.3.5 → v0.3.11)**: body 배경 제거 빠름(2000회) 104.9 s → **24.8 s**(폰이 식은 상태, v0.3.10), 품질 그대로(검증 40.05 dB). 타원 타일 판정, 스플랫별 역전파(bucket), CPU 왕복 제거(10회 묶음 제출), 최적화 분리, 정렬 간접 dispatch, 시작 검증 단축. 사용자 판단: "속도는 이제 충분" → 품질(M4)로 넘어감. 남은 후보: 발열 시 성능 저하(MODERATE에서 약 2배 느려짐, ADPF), sparse Adam, fp16.

### M6 — 견고성 `v0.7` · 2~3 사이클

**구현**: 학습 중 카메라 포즈 미세 보정, 프레임별 노출 · 화이트밸런스 보정, **피사체 움직임으로 어긋난 키프레임 자동 제외**, floater 제거, 자동 크롭 + 박스 미세 조정, 추적 품질이 나쁜 구간 자동 제외, (선택) 촬영 중에 학습을 미리 시작

**사용자 테스트**: 어려운 조건 (전신, 민무늬 옷, 긴 머리카락, 실내 조명 변화)

**완료 기준**: 표준 장면과 어려운 장면 1종 이상에서 눈에 띄는 개선

### M7 — 사용성 마무리 `v1.0` · 1~2 사이클

**구현**: 스캔 갤러리 (썸네일, 이름 변경, 삭제), SPZ / PLY 공유, 백그라운드 학습 (Foreground Service), 크래시 로그 수집, 설정 정리, (가능하면) 다른 기기 테스트

**완료 기준**: 촬영 → 학습 → 공유 전체 과정을 설명 없이 할 수 있음

### 확장 후보 (v1.0 이후)

촬영 중 실시간 학습 · 미리보기, LOD · 압축 학습, 2DGS · 메쉬 추출, ARCore 미지원 기기를 위한 온디바이스 SfM, 여러 기기 지원 매트릭스

## 8. 실험 · 평가 계획

- **표준 장면** (버전마다 같은 조건으로 다시 촬영하거나 같은 스캔을 재사용)
  - **P0 정지 대용물**: 의자에 올려둔 인형·마네킹·옷을 입힌 물체 등. 완전히 정지해 있으므로 사람의 미세한 움직임 문제와 파이프라인 문제를 분리해서 볼 수 있다. 새 기능은 항상 P0부터 확인
  - **P1 앉은 상반신**: 의자에 앉은 사람, 가슴 위로. 기본 시나리오
  - **P2 서 있는 전신**: 서 있는 사람, 머리부터 발까지. 촬영 범위가 넓고 움직임이 커서 가장 어려움
  - 촬영 환경: 가능한 한 같은 장소 · 조명. 배경에 가구나 물건이 보여 ARCore 추적이 잘 되는 곳
  - **가상 촬영 (v0.4~)**: V-head(사람 머리 스캔 흉상), V-body(전신 캐릭터), V-lizard(실제 Scaniverse 스캔). 카메라 포즈가 정확해 학습 코드 검증의 기준으로 쓴다. 정확한 깊이(`depth_gt`)가 있어 형상 오차도 잴 수 있다
- **지표**: hold-out PSNR / SSIM (키프레임 8장마다 1장을 평가용으로 분리, 인물 마스크 영역 기준), 얼굴 영역 PSNR, 학습 시간 (전체 · iteration당 · 단계별), 최대 메모리, 온도 변화, 가우시안 수, 파일 크기, 뷰어 FPS
- **비교 기준** (가능할 때): 같은 데이터셋으로 PC(gsplat 등)에서 학습한 결과, Scaniverse 등 기존 앱으로 같은 장면을 처리한 시간과 화질
- **기록**: `docs/experiments/`에 버전별 결과 표와 피드백 요약을 쌓아 성능 회귀 여부를 추적

## 9. 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| GPU 계열별 드라이버 차이 (Adreno / Mali·Immortalis / Xclipse / PowerVR) | 커널 오동작, 성능 편차 | M0 진단으로 확인, 기능별 fallback 경로, lavapipe 정합성 테스트 |
| float atomic 미지원 또는 느림 | backward 성능 저하 | CAS 에뮬레이션 / atomic-free 경로 |
| ARCore 포즈 drift · 스케일 오차 | 흐릿함, 이중상 | 짧은 촬영 권장, 학습 중 포즈 보정(M6), 추적 품질 낮은 프레임 제외 |
| CPU 이미지 해상도 제한 (기본 640×480) | 디테일 한계 | 고해상도 CameraConfig, Shared Camera (후순위) |
| 자동 노출 · 화이트밸런스 변화 | 색 얼룩 | 프레임별 색 보정 (M6) |
| 발열 스로틀링 | 학습 시간 증가 | ADPF 연동, 동적 작업량 조정 |
| 메모리 부족 / GPU 워치독 | 앱 종료 | 예산 자동 결정, dispatch 분할, 체크포인트 재개 |
| 원격 디버깅의 어려움 | 수정 지연 | 진단 패키지, 단계별 계측, 사용자 데이터셋을 Linux 엔진으로 재현 |
| 목표 시간 (≤ 2분) 미달 | 핵심 목표 미달 | 단계별 목표 (5분 → 3분 → 2분), 초기화 품질에 투자, 해상도·예산 트레이드오프를 프리셋으로 제공 |
| 라이선스 | 배포 제약 | 원본 3DGS 코드 미사용, Apache-2.0 / MIT 계열만 사용 |
| 피사체(사람)의 미세한 움직임 | 얼굴·손 주변 흐림, 이중상 | 짧은 촬영 유도, P0 대용물로 문제 분리, 어긋난 키프레임 제외(M6) |
| 민무늬 옷 · 근접 촬영 시 추적 불안정 | 포즈 오류 | 배경이 보이는 거리 안내, 추적 품질 낮은 프레임 제외 |
| 인물 분할 오류 (머리카락 경계 등) | 머리카락 잘림, 배경 섞임 | 마스크 경계를 부드럽게 처리, 여러 시점 마스크로 보정, 배경 포함 옵션 |
| 개인정보 (얼굴 이미지) | 의도치 않은 공유 | 기기 내 처리, 피드백용 출력물에 이미지 제외, 공유는 사용자가 선택 |
| 폴더블 화면 전환 | 작업 중단 · 재시작 | 화면 구성 변경을 앱이 직접 처리, ViewModel에 상태 유지 |
