# v0.3.10 — 역전파 구조 변경(스플랫별 병렬), CPU 왕복 제거

v0.3.9 결과 (body, 배경 제거, 빠름): **52.3 s**, 검증 40.05 dB. 1회 약 26 ms 중 GPU 23.3 ms, 그중 **역전파 14.2 ms(61%)**. 나머지 약 2.6 ms는 GPU가 CPU를 기다린 시간.

## 병목 분석
1. **역전파 (가장 큼)**: 지금까지의 방식(serial_cut 등)은 스레드 하나가 픽셀 하나를 맡고, 스플랫마다 타일 256픽셀의 그래디언트를 공유 메모리에서 두 단계로 더합니다. 스플랫 하나당 barrier 2번이고, 합하는 동안 대부분의 스레드가 놀아서 이 합산이 역전파 시간의 대부분입니다. 방식만 바꿔서는 피할 수 없는 구조 문제입니다.
2. **CPU↔GPU 왕복**: 1회마다 GPU에 두 번 제출하고 두 번 기다렸습니다. 첫 제출은 "쌍 개수"를 CPU로 읽어 오려고 있던 것으로, 한 번 기다릴 때마다 GPU가 0.9~1.0 ms 쉽니다(합 약 2 ms, 10%). 매 단계 디스크립터 셋도 새로 만들었습니다.
3. 그 밖: 최적화 3.3 ms(가우시안마다 자기 쌍을 순서대로 더해 큰 가우시안이 있는 스레드 묶음이 늦어짐), 렌더 3.6 ms, 정렬 0.8 ms → 다음 후보.

## 변경 사항
- **스플랫별 역전파 (bucket, bucket2)** — "Taming 3DGS"(Mallick 외, 2024)의 방식
  - 순전파가 타일의 스플랫 32개마다 각 픽셀의 상태(투과율, 앞쪽 색)를 저장합니다
  - 역전파에서는 스레드 하나가 **스플랫 하나**를 맡아 타일의 256픽셀을 차례로 훑고, 픽셀 상태를 다음 스레드(뒤 스플랫)로 넘깁니다. 그래디언트는 각 스레드의 레지스터에 쌓이므로 **256픽셀 합산 단계가 없어집니다**
  - bucket2는 한 번에 픽셀 2개씩 처리해 barrier가 절반입니다
  - 지금처럼 학습 전 CPU 기준과 그래디언트를 비교해 맞을 때만 쓰고, 실제 학습 중 재측정으로 더 빠른 방식을 고릅니다. 결과가 틀리거나 느리면 자동으로 기존 방식으로 학습합니다
- **GPU 제출 1번에 최대 10회**
  - 쌍 개수를 CPU로 읽지 않고 GPU에서 바로 씁니다(정렬·타일 범위 계산이 GPU 버퍼의 개수를 읽음). 1회 안의 기다림이 없어졌습니다
  - 10회분을 한 번에 기록해 제출하고, 한 번만 기다립니다. 밀도 조정·재측정 직전에서 끊습니다
  - 디스크립터 셋을 한 번 만들어 계속 재사용합니다
  - 쌍 버퍼는 지금까지 본 최대치 + 여유로 잡습니다. 넘치면 그 단계는 모델을 건드리지 않고 건너뛰고 버퍼를 키웁니다(한 번씩 돌릴 때는 다시 실행). 요약에 `쌍 버퍼 초과` 횟수가 나오며 **0이 정상**입니다
- 마지막 단계에서는 역전파 재측정을 하지 않습니다

## PC(lavapipe) 확인
- 그래디언트: bucket·bucket2 모두 CPU 유한차분 기준과 일치, 픽셀당 스플랫 434개(버킷 14개) 장면에서 serial과의 차이 2e-10
- 묶어서 실행 = 한 번씩 실행: 27회 후 결과 완전히 동일(차이 0)
- 쌍 버퍼 초과 후 재실행: 초과 없는 경우와 그래디언트 동일(차이 0)
- body 300회, 역전파만 바꿔 비교(소프트웨어 GPU라 폰과 비율은 다를 수 있음): serial_cut 262 s → bucket 176 s → **bucket2 159 s**, 역전파 590~816 → 285~430 ms, 검증 PSNR 31.37 → 31.38 dB
