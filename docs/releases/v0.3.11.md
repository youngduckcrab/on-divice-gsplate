# v0.3.11 — 시작 검증 단축, 최적화 단계 분리, 정렬 간접 dispatch

v0.3.10 결과 (body, 배경 제거, 빠름, 폰이 식은 상태): **학습 24.8 s** (v0.3.9 52.3 s), 검증 40.05 dB. 같은 단계에서 bucket 역전파가 기존 방식보다 2.7~4.4배 빠름, 1회 GPU 11.1 ms에 CPU 대기 거의 0. 대신 시작 GPU 검증이 8.2 s로 전체 체감 시간의 약 1/4.

## 변경 사항
1. **시작 GPU 검증 단축**
   - 원인: 방식마다 검증용 학습기를 만들 때 가우시안 **30만 개분 버퍼(약 120 MB)** 를 잡고 0으로 채웠습니다. 검증 장면은 가우시안 10~700개라 장면 크기만큼만 잡도록 바꿨습니다
   - 모든 방식을 재지 않고, **serial_cut과 bucket만 CPU 기준과 비교**한 뒤, 픽셀당 스플랫이 길게 쌓인 장면에서 bucket이 serial_cut과 같은 값을 내는지(저장한 픽셀 상태로 이어서 계산하는 부분) 확인합니다. 하나라도 틀리면 예전처럼 전체 방식을 검사합니다
   - 요약 예: `GPU 검증: serial_cut 정상, bucket 정상, 긴 목록 일치 → bucket`
2. **최적화 단계를 셋으로 분리**
   - 쌍 합: 가우시안마다 자기 쌍들의 그래디언트를 더함(레지스터를 적게 써서 길이가 들쭉날쭉한 반복을 더 많이 겹쳐 실행)
   - 기하: 투영을 거꾸로 따라가 위치·크기·회전·불투명도와 SH DC의 Adam
   - SH: 스레드 하나가 SH 계수 **float 하나**를 맡음. 예전에는 스레드 하나가 45개를 45칸 간격으로 읽고 써서 메모리 접근이 흩어졌는데, 이제 이웃 스레드가 이웃 메모리를 씁니다
   - 요약의 `GPU ms/회`에 `최적화 x (쌍 합 · 기하 · SH)`로 나눠 나옵니다
3. **정렬·타일 범위를 실제 쌍 개수만큼만 실행**
   - v0.3.10에서는 쌍 개수가 GPU에만 있어서 버퍼 용량(최대치의 약 1.4배)만큼 띄웠습니다. 이제 GPU가 개수에서 dispatch 크기를 계산해 간접 dispatch로 띄웁니다(정렬 1.5 → 0.8 ms 예상)

## PC(lavapipe) 확인
- 전체 테스트 통과, **Vulkan 검증 레이어 오류 0** (이번에 레이어로 검사해 정렬 셰이더를 공유하던 다른 스캔의 바인딩 누락을 찾아 고침)
- 최적화 분리 전후 그래디언트 동일(SH 계수 포함 CPU 기준 오차 2e-10), 수렴 테스트 25.13 → 36.83 dB 동일
- 묶음 실행 = 한 번씩 실행(차이 0), 쌍 버퍼 초과 후 재실행 차이 0
