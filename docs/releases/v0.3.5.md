# v0.3.5 — 폰 GPU에서 검증된 역전파만 사용

v0.3.4 자가 검사로 원인이 한 곳으로 좁혀졌습니다.
- 공유 메모리 원자 연산은 정상(max 250/250, add 32640/32640) → atomicMax는 원인이 아니었음
- 순전파 기록(픽셀별 기여 수)은 정상, 파라미터 갱신 단계도 정상
- **역전파(shared 방식)만 틀림**: 36개 쌍 중 1개만 값이 있고 나머지는 0 (PC에서는 28개)
- subgroup 연산은 아주 작은 검사용 셰이더조차 컴파일 실패 → 드라이버가 subgroup 산술 자체를 거부

## 변경 사항
- **새 역전파 방식 "serial"**: 폰에서 정상 동작하는 순전파와 같은 구조로 다시 짰습니다 (반복문 한 단계, 가우시안을 하나씩, 공유 메모리 합을 두 단계로). 기존 shared 방식은 반복문 안의 반복문에서 barrier를 쓰는 구조였는데 폰에서 이 부분이 0을 냈습니다
- **학습 시작 전에 폰 GPU에서 직접 검증**: 역전파 방식을 빠른 순서(subgroup → subgroup 스칼라 → serial → shared)로 시도해서, 그래디언트가 CPU 기준값과 **실제로 맞는 첫 번째 방식**으로 학습합니다 (앱 실행 후 처음 한 번, 1초 안쪽). 맞는 방식이 하나도 없으면 학습하지 않고 오류를 보여 줍니다. 앞으로 드라이버 문제가 있어도 "학습되는 척하지만 아무것도 안 바뀌는" 일은 없습니다
- 자가 검사: subgroup 기능을 하나씩(기본 내장값 / elect / id / 덧셈 / ballot) 따로 컴파일해 보고 어느 것이 거부되는지 표시 — 나중에 빠른 방식을 살리는 데 씁니다
